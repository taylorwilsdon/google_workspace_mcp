# Workspace administration capability coverage

Status as of 2026-09-26. This is **registered operations plus an offboarding workflow**, not complete Workspace administration. Every registered operation is callable through `admin_operation`, which accepts only a registry operation ID with schema-checked parameters and body, fixes customer parameters to the admin's own customer, and checks every user, group, member, domain, role, organizational unit, Cloud Identity resource name, Chrome browser profile and policy target, Directory device, printer, print server, building, calendar resource, and feature ID, and contact or mail delegate against that customer, and every access policy against the Google Cloud organization linked to it. Reads run immediately and return bounded fields. Writes return a one-use proposal, and `confirm_admin_operation` executes it only for the same admin after rechecking identity, customer, permission, and every reference. Excluded methods are refused with their category and reason. Vault and Alert Center take no customer parameter: Google scopes those calls to the signed-in admin's organization, the client is bound to that verified admin, and every account reference or returned alert is checked against the customer. Cloud Identity and Chrome Management clients use the verified credentials with a method table from the pinned discovery documents in `gadmin/discovery/`, because the installed client library's copies are older and lack methods; nothing fetches discovery at call time. Contact Delegation has no public discovery document, so a hand-written document for its three documented methods is pinned there. Gmail delegate settings run only through the existing service-account mode with domain-wide delegation, impersonating a mailbox owner freshly verified in the customer; an admin OAuth grant never builds a Gmail client. The default five-service launcher exposes no admin tools or admin scopes. No tenant admin account, customer ID, OAuth grant, entitlement, or live write has been verified.

## Offboarding boundary

The opt-in tools are `plan_user_offboarding`, `get_offboarding_status`, and `advance_user_offboarding`. Planning reads Directory (user, roles, groups, OAuth grants), Data Transfer applications and existing transfers, and the pinned licensing products; it creates a private workflow record but sends **no Google writes**. The plan names Google-supported transfer applications, missing applications, existing access, and possible data loss. The workflow handles direct group membership, not every delegated permission or inherited group membership. An unsupported transfer application, uncertain transfer, incomplete license lookup, inherited group membership, or uncertain session sign-out stops for manual action. Do not interpret an API-step `completed` state as a certification that all data, Vault retention, or delegated access has been handled.

Delegated access is checked only when its opt-in service is selected, and Vault holds are checked at planning only with `admin-vault`. The plan's gaps name what was not checked:

- **Contact delegation** (`admin-contact-delegation`; [guide](https://developers.google.com/workspace/admin/contact-delegation/guides/manage-delegates), [reference](https://developers.google.com/workspace/admin/contact-delegation/reference/rest)): planning lists the user's delegates (addresses only, at most 10 pages) and adds a `remove_contact_delegates` step after token revocation. Each advance lists afresh and removes one delegate after its own one-use confirmation, bound to the proposed delegate; a delegate still listed after an attempt stops for manual review, and deletion rechecks that none remain. Google offers no lookup of the users who delegated to this user, so that direction is a manual gap. The guide requires the Contacts administrator privilege and contact sharing turned on; this is not verified against a tenant.
- **Gmail mail delegation** (`admin-gmail-delegates`; [guide](https://developers.google.com/workspace/gmail/api/guides/delegate_settings), [reference](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.settings.delegates)): every method is "only available to service account clients that have been delegated domain-wide authority". In service-account mode, planning lists the mailbox's delegates (address and verification status) as a manual gap; the workflow never removes them. Otherwise, or if the read fails, the gap says they were not checked.
- **Vault holds** (`admin-vault`): no API lists holds by account, so planning (when selected) and every final-deletion step page open matters (at most 5 pages of 100) and each matter's `FULL_HOLD` holds (at most 5 pages of 100). An account hold covers the user when it names the user's ID or address; an org-unit hold covers the user when its unit, resolved with a fresh Directory read, is the user's unit or an ancestor. Only matter ID, hold ID, and corpus are recorded. A failed page, permission error, bound overrun, unexpected hold shape, or unknown corpus makes the result unknown. The check runs before the deletion is proposed and again at its confirmation. A covering hold, an unknown result, or a missing Vault client blocks the final deletion, even for a plan made without Vault; there is no override. Earlier steps run without Vault. Retention rules and matters the admin cannot see are always listed as manual gaps; finding no hold never certifies that data is preserved.

Advances suspend the account, sign out sessions, revoke recorded OAuth tokens, submit a transfer, **wait for Google to report both overall and per-application completion**, remove direct group memberships and licenses, and propose final account deletion separately. A call makes at most one Google write. Account deletion is blocked if transfer, known groups, tokens, or pinned license products are incomplete, or if a fresh Vault hold check cannot confirm that no hold covers the user. Suspension, each license removal, and deletion require a separate short-lived one-use server-side confirmation tied to the actor, customer, target, action, and exact payload. Each advance rechecks the admin identity and customer, the target and recipient, and configured operation permissions. A workflow file (0600 in a 0700 directory) persists the actor, steps, pending attempt, and transfer ID; confirmations live separately as token hashes. Each save syncs the workflow file and its directory before the next Google write. Failed or uncertain writes are reconciled against Google before retry, and an unreconcilable outcome requires manual review. Every attempted write is audited as accepted, failed (a definitive refusal), or unknown (HTTP 408, 429, 5xx, or a transport error). Audit records are restricted to safe identifiers and field names, never token values or Vault contents.
